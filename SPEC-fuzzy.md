**Specification: Fuzzy Matching Decoder for 128-bit Number + 7-bit Checksum from 3 Natural Language Sentences**

* **Version:** 1.0 (Fuzzy Decoder Addendum to v6.2)
* **Date:** May 2, 2025
* **Based On:** Specification v6.2 (Encoder/Exact Decoder) dated April 30, 2025
* **Author:** Gemini AI (based on user requirements)

**1. Introduction**

This document specifies the requirements for a **Fuzzy Matching Decoder** software module. It builds upon the encoding logic defined in Specification v6.2 but modifies the decoding process significantly.

The goal of this decoder is to reconstruct the original 128-bit unsigned integer from a sequence of **three potentially imperfect natural language sentences**. These input sentences are expected to approximate the structured sentences generated by the v6.2 encoder (`CharacterPhrase SettingPhrase ActionPhrase ObjectPhrase OutcomePhrase`).

Unlike the exact decoder in v6.2, this module attempts to tolerate variations in the input sentences (e.g., typos, synonyms, minor rephrasing) using fuzzy matching techniques. Due to the nature of fuzzy matching and the limitations of the 7-bit checksum, this decoder **does not guarantee a unique or even correct result**. Instead, it aims to produce a **list of all possible 128-bit candidates** that could plausibly correspond to the input sentences and satisfy the checksum validation.

**Compatibility with the v6.2 encoder's output structure and logic is essential.** The encoding process itself remains unchanged.

**2. Core Concept**

1.  **Encoding Reference (v6.2):** An initial 128-bit number has a 7-bit SHA256 checksum calculated and appended, forming a 135-bit sequence `N`. `N` is split into three 45-bit chunks. Each chunk provides 5 indices (10, 10, 8, 9, 8 bits) used to look up exact phrases from 5 dictionaries (`character`, `setting`, `action`, `object`, `outcome`). These 5 phrases are concatenated with single spaces to form one sentence per chunk, resulting in 3 precise output sentences.
2.  **Fuzzy Decoding:**
    a.  Takes 3 input sentences, which may contain errors compared to the encoder's output.
    b.  For each sentence, attempts to identify sequences of 5 phrases (one from each corresponding dictionary) that are a "close match" to the input sentence, using fuzzy matching algorithms. This may yield *multiple* candidate sequences of phrases (and thus indices) per input sentence.
    c.  Generates all possible combinations by taking one candidate index sequence from each of the three sentences.
    d.  For each full combination (3x5 indices), reconstructs the 135-bit number.
    e.  Separates the 135 bits into the 128-bit potential data payload and the 7-bit potential checksum.
    f.  Calculates the *actual* 7-bit SHA256 checksum for the reconstructed 128-bit data payload.
    g.  Compares the calculated checksum with the potential checksum extracted from the 135 bits.
    h.  If they match, the 128-bit data payload (formatted as hex) is considered a valid candidate solution.
    i.  The final output is a list containing **all** such valid candidate solutions found.

**3. Data Structures and Formats**

* **Input:** An ordered list or array containing exactly **3** strings (potentially imperfect sentences). UTF-8 encoding is expected.
* **Output:** An ordered list or array containing **zero, one, or multiple** strings. Each string in the output list is a 32-character, lowercase hexadecimal representation of a 128-bit data payload that passed the checksum validation. An empty list indicates no combination of fuzzy matches satisfied the checksum.
* **Dictionaries:** Uses the same 5 dictionary files as specified in v6.2 ( `character_10bit.txt`, `setting_10bit.txt`, `action_8bit.txt`, `object_9bit.txt`, `outcome_8bit.txt`). Loading, format requirements (UTF-8, one phrase per line, may contain spaces), and error handling remain the same. Efficient forward (index -> phrase) and reverse (phrase -> index) lookups are required.
* **Bit Allocation & Order:** Same as v6.2 (135 bits = 128 data + 7 checksum; 3x45 bit chunks; 10+10+8+9+8 bits per component).
* **Checksum Calculation:** Same as v6.2 (first 7 bits of SHA256 of the 128 data bits).

**4. Fuzzy Decoding Process (Algorithm)**

1.  **Input Validation:** Receive `input_sentences` list. Verify it contains exactly 3 strings.
2.  **Load Dictionaries:** Load all 5 dictionaries into memory. Create efficient forward and reverse lookup structures (e.g., list/array for index->phrase, hash map/dictionary for phrase->index). Handle file/format errors per v6.2.
3.  **Initialize:** `valid_hex_results = []`.
4.  **Generate Sentence Candidates (Loop i from 0 to 2):**
    a.  Get sentence string `s = input_sentences[i]`. Trim whitespace.
    b.  **Parse Sentence with Fuzziness:** This is the core fuzzy logic step. The goal is to find all plausible sequences of 5 dictionary indices `(idx_c, idx_s, idx_a, idx_o, idx_k)` whose corresponding phrases, when concatenated with spaces, "closely match" the input sentence `s`.
    i.  **Strategy:** Implement a recursive or iterative approach to segment the sentence `s` and match segments against dictionary entries using a chosen fuzzy matching technique.
    ii. **Segmentation & Matching Example (Recursive Approach):**
    * Define a function `find_fuzzy_sequences(current_sentence_part, component_index, dictionaries)`.
    * **Base Case:** If `component_index == 5`: If `current_sentence_part` is "empty" (or whitespace), return `[[]]` (a list containing an empty list, signifying success). Otherwise, return `[]` (failure).
    * **Recursive Step:**
    * Get the appropriate dictionary `D = dictionaries[component_index]`.
    * Initialize `matches = []`.
    * Iterate through possible segmentation points `k` of `current_sentence_part`. Let `prefix = current_sentence_part[0:k]` and `remainder = current_sentence_part[k:]`.
    * For the `prefix`, compare it against *all* entries `e` in dictionary `D` using the chosen fuzzy matching algorithm (see Section 5).
    * If `fuzzy_match(prefix, e)` meets the defined threshold:
    * Get the index `idx` of `e`.
    * Recursively call `sub_sequences = find_fuzzy_sequences(remainder.strip_leading_space(), component_index + 1, dictionaries)`.
    * For each `seq` in `sub_sequences`, prepend `idx` to it (`[idx] + seq`) and add it to `matches`.
    * Return `matches`.
      iii. **Result:** This process should yield a list `sentence_candidates[i]` containing all plausible 5-tuples of indices found for sentence `i`. Example: `sentence_candidates[0] = [(12, 345, 6, 100, 200), (15, 345, 6, 101, 200), ...]`.
      iv. **Handle Errors:** If no plausible sequence is found for a sentence, `sentence_candidates[i]` will be empty.
5.  **Combine Candidates & Verify:**
    a.  If any `sentence_candidates[i]` list is empty, no solution is possible. Return `valid_hex_results` (which is empty).
    b.  Generate all combinations by taking one 5-tuple of indices from `sentence_candidates[0]`, one from `sentence_candidates[1]`, and one from `sentence_candidates[2]`.
    c.  For *each combination* of three 5-tuples:
    i.  **Reconstruct 3 Chunk Values:** For each 5-tuple `(idx_c, idx_s, idx_a, idx_o, idx_k)`, calculate the 45-bit `chunk_value` using the bit shifts defined in v6.2 (Sec 5d).
    ii. **Reconstruct 135-bit Number:** Combine the three `chunk_value`s: `reconstructed_135_num = (chunk1 << 90) | (chunk2 << 45) | chunk3`.
    iii. **Separate Data and Checksum:**
    * `checksum_bits_decoded = reconstructed_135_num & 0x7F`.
    * `data_num_decoded = reconstructed_135_num >> 7`.
      iv. **Verify Checksum:**
    * Convert `data_num_decoded` (128 bits) to 16 bytes `data_bytes_decoded`.
    * Calculate `sha256(data_bytes_decoded)`. Get the first 7 bits `checksum_bits_calculated`.
    * **If `checksum_bits_calculated == checksum_bits_decoded`:**
    * Convert `data_num_decoded` into a 32-character hex string, lowercase, zero-padded (`valid_hex`).
    * If `valid_hex` is not already in `valid_hex_results`, add it.
6.  **Output:** Return the `valid_hex_results` list.

**5. Fuzzy Matching Parameters and Techniques**

The implementer must choose and implement a fuzzy matching strategy. This should be configurable.

* **Required Technique:** Levenshtein Distance
    * Parameter: `max_levenshtein_distance` (integer, e.g., 1, 2, 3). A match occurs if the edit distance between the input segment and a dictionary phrase is less than or equal to this value.
* **Optional Techniques:**
    * **String Similarity Metrics:** (e.g., Jaccard index, Cosine similarity on character n-grams). Parameter: `min_similarity_threshold` (float, e.g., 0.8).
    * **Synonym Matching:** Requires an external or configurable synonym list mapping synonyms to dictionary phrases. Parameter: `enable_synonyms` (boolean). If enabled, the parser should also consider matches via synonyms.
* **Configuration:** These parameters (`max_levenshtein_distance`, `min_similarity_threshold`, `enable_synonyms`, potentially synonym file path) should be configurable at runtime or via a configuration file.

**Important Note on Parsing:** The parsing logic (Step 4.b) must correctly handle potential ambiguities where dictionary phrases are prefixes of others, especially when combined with fuzzy matching. The strategy should aim to find *all* plausible parsings that meet the fuzzy criteria.

**6. Error Handling**

Handle and report errors including:
* Invalid input format (not 3 sentences).
* Dictionary file issues (missing, wrong size, format errors).
* Parsing failure (even with fuzziness, unable to construct any plausible sequence for a sentence).
* **Output Indication:** An empty output list `[]` is the standard way to indicate that no combination of fuzzy-matched phrases resulted in a valid checksum. This is not necessarily an error, but rather the result of the fuzzy search.

**7. Performance Considerations**

* **Combinatorial Explosion:** The number of candidate combinations (Step 5b) can grow very large, leading to significant computation time.
* **Fuzzy Comparison Cost:** Fuzzy matching each potential segment against all dictionary entries is computationally intensive.
* **Optimizations:**
    * Implement efficient dictionary lookups and fuzzy matching algorithms.
    * Consider pruning the search space during parsing (Step 4b) by discarding paths with very poor cumulative fuzzy match scores.
    * Limit the maximum number of candidates per sentence or the total number of combinations to check, if necessary, though this might risk missing the correct solution.

**8. Disclaimer**

This fuzzy decoder attempts to recover data from imperfect input but provides **no guarantee of correctness or uniqueness**. The 7-bit checksum is a weak filter against incorrect matches generated by the fuzzy logic. The output is a list of possibilities, which could be empty, contain the single correct result, contain multiple results (including the correct one and others that coincidentally pass the checksum), or contain only incorrect results that coincidentally pass the checksum. Use with caution and awareness of these limitations.
